# Loader ELF64 w Ring 3 — etap 1.1 (2026-11-12)

Pierwszy krok planu rozwoju: obraz ELF64 z obcego kompilatora jest od teraz
czytany, walidowany, mapowany i **uruchamiany** jako proces Ring 3. Wcześniej
loader rozpoznawał ELF wyłącznie po magic i raportował go jako
`elf-ok:Nseg` bez mapowania — żadne binarium z gcc/clang/musl nie mogło
wystartować.

## 1. Punkt wyjścia (stan w kodzie, nie w dokumentacji)

| Obszar | Przed |
|---|---|
| Mapowanie ELF | brak. `loader_status_formatu()` tylko rozpoznawał i zwracał status |
| Jedyny wykonywalny format | `.bur` v1 i v2 |
| Odczyt obrazu z PSF | `bsp_wczytaj_obraz_bur()` — walidował nagłówek BUR, więc plik ELF nie przechodził |
| Stos Ring 3 | 256 KiB dla `.bur` |
| ET_DYN | statyczny PIE z load bias i `R_X86_64_RELATIVE`; brak linkowania dynamicznego |

## 2. Zmiany

### 2.1 `jadro/fs/elf_loader.{h,cpp}` — rozpoznanie typu

Nowa funkcja `elf_typ()` zwraca `e_type` po pełnej walidacji albo `0`.
Wartość `0` nie jest żadnym poprawnym `e_type`, więc loader nie może pomylić
„niepoprawny obraz" z `ET_EXEC`.

### 2.2 `jadro/fs/psf.{h,cpp}` — surowy odczyt obrazu

`bsp_wczytaj_obraz_binarny()` czyta plik bez interpretacji nagłówka, z tym
samym kontraktem bezpieczeństwa co ścieżka BUR: rozmiar sprawdzany **przed**
alokacją, wynik jest prywatną kopią w pamięci jądra, zwolnienie należy do
wywołującego.

### 2.3 `jadro/fs/loader.cpp` — mapowanie i uruchomienie

- `mapuj_segment_elf()` — mapuje jeden `PT_LOAD`. Ramka jest wypełniana przez
  alias HHDM **przed** utworzeniem PTE użytkownika, więc segment kodu nigdy
  nie istnieje jako jednocześnie zapisywalny i wykonywalny. BSS powstaje przez
  wyzerowanie ramki i skopiowanie wyłącznie przecięcia strony z `p_filesz`.
- `uruchom_elf_impl()` — odczyt, walidacja (`elf_waliduj`), opcjonalny
  statyczny PIE (`ET_DYN`), `elf_opisz`, kontrola okna adresowego, podpis, mapowanie,
  publikacja. Przy każdym błędzie PID jest zwalniany **dokładnie raz**.
- `opublikuj_proces_uzytkownika()` — wspólny ogon dla `.bur` v1, `.bur` v2
  i ELF64. Wydzielony świadomie: duplikacja ramy `iretq`, CR3, pól `proces_t`
  i publikacji `PROCES_GOTOWY` to najkrótsza droga do rozjazdu w mechanizmie
  bezpieczeństwa.
- Rozpoznanie formatu **przed** odczytem całego obrazu: 4 bajty magii decydują,
  który loader jest wywoływany.

### 2.4 Ograniczenia adresowe (jawne, nie domniemane)

| Stała | Wartość | Dlaczego |
|---|---|---|
| `ELF_MAKS_GORNY_ADRES` | `RING3_HEAP_BASE` (32 GiB) | obraz nie może wejść w stertę, SHM, mmap ani stos |
| `LICZBA_STRON_STOSU_ELF` | 512 (2 MiB) | programy upstream zakładają realny zapas |
| `GORNA_BAZA_STOSU_ELF` | `RING3_STACK_TOP - 2 MiB` | szczyt nie wychodzi ponad okno Ring 3 |
| `static_assert` | stos > sterta + 1 GiB | wykrywa kolizję okien już przy kompilacji |

### 2.5 Polityka integralności

Identyczna jak dla `.bur`: paczki z `/programy/` i `/gry/` są zaufane przez
pochodzenie medium ISO, wszystko inne wymaga podpisu RSA-2048. Weryfikacja
odbywa się **przed** alokacją pierwszej ramki.

### 2.6 Statyczny `ET_DYN` / PIE

Loader obsługuje minimalny, statyczny wariant PIE:

- `elf_zbierz_relokacje()` czyta wyłącznie `SHT_RELA` z tablicy sekcji,
- akceptowana jest tylko bezsymbolowa `R_X86_64_RELATIVE`,
- każda relokacja musi wskazywać ośmiobajtową komórkę w zapisywalnym
  `PT_LOAD`; pozostałe typy, symbole i cele są odrzucane przed mapowaniem,
- load bias jest wyrównany do strony i losowany z okna pomiędzy `RING3_BASE`
  a `RING3_HEAP_BASE`; cały obraz pozostaje poniżej sterty, mmap/SHM i stosu,
- bias aktualizuje `e_entry`, `AT_ENTRY`, `AT_PHDR` oraz adresy segmentów.

Walidacja i obliczenie `B + A` są testowane hostowo pod ASan/UBSan. Gate QEMU
pozostaje ET_EXEC, ponieważ testuje ABI SysV i VFS, a nie powinien udawać
pełnego testu dynamicznego linkowania.

### 3.1 Co dokładnie sprawdza `test-elf-exec-qemu`

Obraz jest budowany `x86_64-linux-gnu-g++` z własnym skryptem linkera,
`ET_EXEC` pod `0x2100000`. Test podmienia blob aplikacji testowej w obrazie
ISO (produkcyjny `BursztynOS.iso` nie jest dotykany) i sprawdza w Ring 3:

1. kod `.text` się wykonuje,
2. bramka SysV (`int 0x80`) działa z procesu załadowanego z ELF,
3. `.data` skopiowane z pliku, `.bss` wyzerowane, `.rodata` czytelne,
4. stos 2 MiB — zapis 1,5 MiB nie wywołuje `#PF` (stos `.bur` by nie wystarczył),
5. `uname(2)` raportuje `BursztynOS` / `x86_64`,
6. `write(1)` zwraca długość i tekst trafia do logu szeregowego.

### 3.2 Błąd znaleziony i naprawiony w teście

Pierwsze uruchomienie dało 5/6: `write(1)` zwracał 0. Przyczyna była w teście,
nie w jądrze — trzeci argument SysV trafiał do `R10` (czwarty argument ABI)
zamiast do `RDX`. Po poprawce 6/6. Zostawiam to w raporcie, bo pokazuje, że
test faktycznie sprawdza zachowanie, a nie tylko „coś się uruchomiło".

## 4. Czego świadomie NIE ma

| Brak | Dlaczego |
|---|---|
| `ET_DYN` / PIE | tylko statyczny wariant z `SHT_RELA` i `R_X86_64_RELATIVE` |
| Linkowanie dynamiczne | `PT_INTERP` / `PT_DYNAMIC` nadal odrzucane ze statusem `ELF_LINKOWANIE_DYNAMICZNE`; brak `ld.so`, libc.so, GOT/PLT i symbol resolution |
| Demand paging | mapowanie jest eager, jak dla `.bur` |
| `mprotect` | nadal `-ENOSYS`; VMM nie ma API zmiany flag istniejącego mapowania |
| Exec z argumentami `argv`/`envp` w stylu POSIX | rama `_start` pozostaje bezargumentowa; to punkt 3.3 planu (user space) |

## 5. Kolejny krok

Punkt 1.2 planu: tablica deskryptorów plików (`jadro/vfs/`) i rozszerzenie
bramki SysV o `open`/`read`/`lseek`/`fstat`/`brk`. Bez tego musl nie wystartuje
nawet jako `hello world`, bo jego `crt1` otwiera `/etc/...` przed `main`.
